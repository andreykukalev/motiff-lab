# The Motiff Lab iPad app

**Status (2026-11-16):** the only actively developed client ([0032](../../docs/architecture/adr/0032-ipad-first-web-archived.md)). The web app is archived in `archive/web`; the files this app shares with it live in [`src/shared`](../shared/README.md): the score, roll, layout, storage and playback modules (`Scripts/…`, compiled by `dotnet build src/shared`), the interface words, the piano and the example piece ([`docs/repository-structure.md`](../../docs/repository-structure.md)). The app never imports the frozen web code, and its build needs no web publish, deploy or browser test.

A native SwiftUI app over the same C# music-core as the web app (decision record [0019](../../docs/architecture/adr/0019-native-ipad-app.md)). Swift draws the screens; everything musical comes from music-core through its facade ([0020](../../docs/architecture/adr/0020-music-core-facade.md)), and the score is engraved by the same Verovio as the web's.

```
SwiftUI (App/MotiffLab)  ->  MotiffLabCore.xcframework  ->  ml_version / ml_open / ml_call / ml_close / ml_free
                                                             -> Core/Exports.cs -> src/backend/MotiffLab.MusicCore (unchanged)
                         ->  Verovio.xcframework         ->  Verovio's C API (tools/c_wrapper.h), A4 pages in Leland
```

| Folder | What it holds |

So far the app opens a MIDI, MusicXML or project file from Files, or the example, keeps each piece as a `.motiff.json` project file in its Documents (shown in the Files app, saved when the score closes or the app leaves the screen), shows its score on A4 pages, takes Apple Pencil marks on it (in the simulator, which has no Pencil, the mouse writes with Pen on and two fingers on the trackpad scroll) and plays it. The score page (`App/Web`) runs the web app's own score modules (`Scripts/score`, compiled to `wwwroot/js/score`): the app draws the live stroke as the page will keep it (`InkInput.swift`, the page's own outline with its pressure and grain), the page keeps it against its bar as the web does, and music-core saves it in the project file (`marks.ink`), so a mark made on the iPad shows in the web app and back. Playback is `PlaybackEngine.swift`, a port of the web's engine (`Scripts/playback/playback-processor.ts`, 0007) run by `AVAudioEngine`, with the same piano, tempo from 25 to 150%, metronome, and the pedal as music-core writes it into the notes. Settings (the person button on the first screen) signs in with MSAL to the web app's External ID tenant and registration (`App/MotiffLab/Account.json`, the published web app's own values; the redirect `msauth.com.andreykukalev.motifflab://auth` is added by `infra/azure/ipad.ps1`), shows the plan the API answers, and gives testers the Pro and no Pro switch, sent as `Motiff-Plan` as the web app sends it. A Mac that signs the app with another bundle identifier needs that redirect registered too. It is the Practice Studio of the two workspaces of one product ([0025](../../docs/architecture/adr/0025-two-studios.md)): it shares music-core, the project file and the design kit with the web app, and its functions are chosen for working with the music at the instrument, not copied from the web app. The design kit is read from `tokens.css` in Daylight and Night with the kit's faces registered at launch (`Design.swift`), and the library is the shelf of cards, each card read from its project file by music-core (`project.summary`). For a couple of hundred pieces (version 0.2, Andrei's approved screens in the project's ux-prototype/v2, lib-1, lib-3 and lib-4) it is a list with Title, Composer, Playlists and Opened columns, each heading but Playlists ordering it, and an A–Z index at the edge, in tabs: All pieces, Composers (each with how many pieces, then theirs), Recent, Playlists (the same), and Sessions, the cards of current work; it is searched by title, composer, tag and playlist whatever the letter case and accents and filtered by a composer, a tag and a playlist, the web app's rules (`LibraryShelf.swift`). A long press on a piece opens its properties (title, composer with the library's composers offered while typing, tags, and the playlists it is on, ticked, with «New playlist»), which music-core writes into its project file (`project.metadata`), so the web app shows them too. Signed in, the pieces sync with the web app by themselves (version 0.2, `CloudSync.swift`, the rules in music-core's `ProjectSync` through `project.sync`, `project.online`, `project.pulled` and `project.resolve`): when the library opens, comes back to the screen, after a piece closes and on sign-in, each piece changed here is sent with `If-Match`, one new or changed online comes here keeping this iPad's PDF, and when both changed one, the last save wins and the other copy is kept beside as a piece of its own. One piece is one entry (version 0.6.1): after each pass the projects here that are the same piece by the files they were made from (`project.summary`'s `pieceKeys`, grouped by `project.same`), such as the same PDF added on the web and on the iPad, become one when one of them carries nothing of the player's own (`project.join`, music-core's `SamePiece`): the other is kept with its PDF and details, and the copy is deleted here and online; one whose PDF is linked or kept on this iPad stays. What the iPad knows of each online copy is in `sync.json` in Application Support (`sync-test.json` for the Test environment, [below](#main-and-test-environments)). A piece that is only a PDF stays here; a free account keeps 300 pieces online, and the library says how many stay here beyond them. Settings turns it off. The app's icon is `AppIcon.xcassets`, rendered from the product's icon.

Version 0.5 adds «Импорт папки» (an experiment until v0.6.5, when every iPad experiment became part of the app and Settings lost its Experimental section). «Добавить папку» in Add piece takes a folder in Files, the iPad's or a provider's, and keeps a bookmark of it in Application Support (`LibraryImport/<environment>/folders.json`, `ImportFolders.swift`); a bookmark that does not open again is said (the library's menu, «Нет доступа к папке» with «Выбрать папку заново»), and its pieces are then copies on the iPad. The folder is listed without downloading it and each file read once by a coordinated read (`FolderScan.swift`); music-core plans the import (`library.plan`) and «Что нашлось» (`FolderFoundSheet.swift`) shows it. The import job (`ImportJob.swift`) adds one file at a time, kept in `job.json` after each, with pause, stop and «Продолжить» after a relaunch, in a banner over the library. A PDF kept by link stays in the folder (`library.linked`); opening it reads it there through this iPad's link and checks its fingerprint (`AwayPieces.swift`, `open` with `pdf`), and «Проверить папку» finds a moved or renamed file again (`library.relink`, `library.link`). «Держать на этом iPad» on a playlist keeps a copy of its PDFs for when there is no connection (`KeptCopies.swift`). «Распознать ноты в нескольких пьесах» (the library's menu) picks PDF-only pieces, also filtered by «Без нот», and after one consent for the batch sends them one at a time to the scan server chosen (`Recognition.swift`, kept in `recognition.json`); Motiff Lab's hosted server reads at most 1000 pages a day for a player (100 until 2026-11-13), counted on the device, the player's own server has no limit. A score of up to 100 pages longer than the server reads in one request goes in parts, one after another, and music-core joins their notes (`ScanParts.swift`, `scan.join`; #479). With Settings · Account · the scan engine set to «Авто», the pages a notation program drew are read on the iPad by music-core's vector reader and only the other pages are sent (`VectorPages.swift`, `scan.vector`; [0029](../../docs/architecture/adr/0029-vector-pdf-reading.md)). «Распознать ноты: сразу для всех» on «Что нашлось» puts each PDF the import adds into the batch. The app never writes, renames, moves or deletes anything in the player's folders. What only one feature folder says is in its `Words/<Folder>.{en,ru}.json` (`App/MotiffLab/Import/Words/Import.en.json`), beside the shared words.

## Build and run (Mac)

You need Xcode 16 or later, XcodeGen and CMake (`brew install xcodegen cmake`) and the .NET 10 SDK (https://dot.net, or `brew install --cask dotnet-sdk`). Terminal must use Xcode's tools: `sudo xcode-select -s /Applications/Xcode.app/Contents/Developer`.

```bash
cd motiff-lab
git pull
src/ipad/Core/build.sh          # 2-4 minutes: music-core with NativeAOT; again after music-core changes
src/ipad/Verovio/build.sh       # 5-10 minutes, once: Verovio from source
dotnet build src/shared         # the shared score scripts, which the app's score page runs
cp src/ipad/App/Config/Local.xcconfig.example src/ipad/App/Config/Local.xcconfig   # once: your DEVELOPMENT_TEAM
cd src/ipad/App && xcodegen && open MotiffLab.xcodeproj
```

A `Local.xcconfig` from the old shell (`ios/Config/Local.xcconfig`) can be moved here as it is. Choose the iPad as the destination and Product > Run (Release). Product > Test (⌘U) runs the Swift tests on the chosen device or simulator. A free Apple ID signs the app for 7 days at a time.

## Checks

- The `iPad` workflow (`.github/workflows/ipad.yml`) builds both frameworks, checks the core's C functions on macOS, runs the Swift tests in the iPad simulator and builds for a real iPad: on every pull request that touches what the app is built from (with each push; its job `ipad-gate` is required on `develop`), on `develop` after such a merge, for every version tag and by hand from the Actions tab. The build for a real iPad is skipped on pull requests. For a tag, nightly on `develop` and by hand with Walk ticked it also walks the `Screens` scheme's journeys (asserting, a few minutes); with Screenshots ticked it walks every appearance and keeps the pictures as the `ipad-screens` artifact (about half an hour, while pull requests' runs queue behind it); either fails when the walk fails ([`docs/repository-structure.md`](../../docs/repository-structure.md#ipad-builds)). It is not part of CI's `build-test`. Swift written in a cloud session is first compiled there.
- On Linux: `dotnet publish src/ipad/Core -c Release -r linux-x64 -o /tmp/core && python3 src/ipad/Core/check.py /tmp/core/MotiffLabCore.so`.

## Releases

Versions follow `governance/README.md`: a test version is a tag `v0.<n>` on `develop`, a stable version a tag on `main`. Install one on the iPad with one command on the Mac:

```bash
src/ipad/build-version.sh v0.1     # or a branch name; then `git switch -` to go back
```

It builds everything from that tag, signs with your team from `Local.xcconfig` (a free Apple ID: 7 days), sets `MARKETING_VERSION` from the tag, and installs on the one connected iPad, or opens Xcode for Product > Run. Run it from an up-to-date clone (`git pull` first): the script you start is the one that runs. Every `v*` tag also runs the `iPad` workflow (the Swift tests in the simulator). TestFlight and the App Store need the paid Apple Developer Program; the old `ipad-v*` tags still work.

### Main and Test environments

`Account.json` carries both server environments ([infra/README.md](../../infra/README.md#the-develop-environment)), with one sign-in (the same tenant and registrations): **Main** (`Account`: the players' API, scan server and real database, the published web app's values) and **Test** (`Environments.Test`: develop's API and scan server and their test database, as the web test site uses). `Environments.Default` is where a build starts; the committed file says `main`, and `src/ipad/build-version.sh` sets it for that build only: a test version (a commit not in `main` yet) starts in Test, a version in `main` in Main; `MOTIFF_SERVERS=main` or `MOTIFF_SERVERS=develop` before the command chooses by hand. It is a tool for Andrei's own testing on one iPad (2026-11-12), not a product feature (`Environments.swift`):

- **Settings → Account → «Окружение: Основное | Тестовое»** ("Environment: Main | Test") switches. Only a test version or an account with the Tester role (the API's `tester`) sees the row, and anyone away from the build's default, so the way back stays; a player of a released version never sees it. Each switch asks first, naming the environment and saying that the library changes, then reloads the library, the plan and the profile from that environment; the sign-in stays. The choice is kept on the iPad, one for test versions and one for released ones.
- **Each environment has its own library on the iPad**: Main's project files are in Documents itself, where every piece was before (so the pieces already on an iPad, synced with main until 0.3, are Main's and never reach the test database), and its sync records stay in `sync.json`; Test's are in `Documents/Test` (a folder Main's library never reads) and `sync-test.json`. Every request of a sync pass goes to the environment the pass started in, and stops when the iPad switches, so no piece passes from one database to the other.
- **Test is always marked**: «Тест» ("Test", in the danger colour) beside the library's name and the environment row.
- **In a test version, Main is read only**: it lists, fetches and opens the real pieces, but sends nothing (no save, no profile, nothing deleted; a piece changed on both sides stays as it is here), and what is changed stays on the iPad; the library says «Основное окружение: только чтение» ("Main environment: read only"). «Разрешить запись в Основное» ("Allow writing to Main") under the row turns writing on, after a warning, for this build only: the next installed build is read only again. In a released version Main is read and written as always.
- **Settings → «О приложении»** ("About") says which build this is: the tag it was built from (`v0.5.2`), or the branch and the commit when it is no tag, the commit and when it was built, all written into the app's Info.plist by `src/ipad/build-version.sh` (a build from Xcode alone says its project version and "dev"), and the environment the iPad works in. In Test it offers «Очистить всё» ("Clear everything", `TestLibrary.swift`) for a new testing cycle: after a confirmation it deletes, signed in, the player's data in the test database (the API's `POST /me/reset`, only on develop's own API), then Test's own files on the iPad (`Documents/Test/*.motiff.json`, `sync-test.json`, `LibraryImport/test`), never Main's and never the player's PDFs, recordings or folders added by link. The reset's stamp reaches the player's other devices with their next list of projects, and each clears its own test library before it syncs (`TestReset`; [infra/README.md](../../infra/README.md#a-fresh-testing-cycle)).
