# The Motiff Lab iPad app

A native SwiftUI app over the same C# music-core as the web app (decision record [0019](../docs/decisions/0019-native-ipad-app.md)). Swift draws the screens; everything musical comes from music-core through its facade ([0020](../docs/decisions/0020-music-core-facade.md)), and the score is engraved by the same Verovio as the web's.

```
SwiftUI (App/MotiffLab)  ->  MotiffLabCore.xcframework  ->  ml_version / ml_open / ml_call / ml_close / ml_free
                                                             -> Core/Exports.cs -> src/MotiffLab.MusicCore (unchanged)
                         ->  Verovio.xcframework         ->  Verovio's C API (tools/c_wrapper.h), A4 pages in Leland
```

| Folder | What it holds |
| --- | --- |
| `Core/` | music-core as a native library: `Exports.cs` (the facade's five C functions, nothing else), `include/motifflab_core.h`, `build.sh` (NativeAOT for the iPad and its simulator → `build/MotiffLabCore.xcframework`), `check.py` (the C functions called on Linux or macOS). In `MotiffLab.slnx`, so CI compiles the exports. |
| `Verovio/` | `build.sh` (Verovio 6.3.0 from source, as a dynamic framework because it is LGPL → `build/Verovio.xcframework` and `build/verovio-data`) and the one-line locale patch, to be offered upstream. |
| `App/` | The SwiftUI app, generated by XcodeGen from `project.yml` (the Xcode project is not committed), with `Config/Base.xcconfig` and your own `Config/Local.xcconfig`. The example piece, the design tokens, the interface's words and the piano are the web app's own files (`src/MotiffLab.Web/Playback/FurElise.musicxml`, `design/kit/tokens.css`, `src/MotiffLab.Web/wwwroot/i18n`, `src/MotiffLab.Web/wwwroot/audio/piano`). |
| `App/Web/` | The score page in the app's web view: `score.html`, `score.css` and `score.js`, which runs the web app's score geometry and pencil marks, served to the web view as `motiff://app/…`. |
| `App/MotiffLabTests/` | Swift tests: the facade through the C functions, opening and engraving a piece, the interface's words, the playback engine (held to the web engine's own tests), the piano, project files, a pencil mark kept, saved, drawn and erased. |
| `App/MotiffLabScreens/` | Screenshots of the screens for the redesign's mockups (scheme `Screens`): a UI test walks the library, the example piece and a PDF piece in Russian, landscape and portrait, light and dark. Debug builds take `-ml-screens-reset` and `-ml-screens-open <path>` for it (`ScreensHook` in `LibraryView.swift`). |
| `build/` | What the two scripts build (not committed). |

So far the app opens a MIDI, MusicXML or project file from Files, or the example, keeps each piece as a `.motiff.json` project file in its Documents (shown in the Files app, saved when the score closes or the app leaves the screen), shows its score on A4 pages, takes Apple Pencil marks on it (in the simulator, which has no Pencil, the mouse writes and two fingers on the trackpad scroll) and plays it. The score page (`App/Web`) runs the web app's own score modules (`Scripts/score`, compiled to `wwwroot/js/score`): PencilKit draws the live stroke, the page keeps it against its bar as the web does, and music-core saves it in the project file (`marks.ink`), so a mark made on the iPad shows in the web app and back. Playback is `PlaybackEngine.swift`, a port of the web's engine (`Scripts/playback/playback-processor.ts`, 0007) run by `AVAudioEngine`, with the same piano, tempo from 25 to 150%, metronome, and the pedal as music-core writes it into the notes. Settings (the person button on the first screen) signs in with MSAL to the web app's External ID tenant and registration (`App/MotiffLab/Account.json`, the published web app's own values; the redirect `msauth.com.andreykukalev.motifflab://auth` is added by `infra/azure/ipad.ps1`), shows the plan the API answers, and gives testers the Pro and no Pro switch, sent as `Motiff-Plan` as the web app sends it. A Mac that signs the app with another bundle identifier needs that redirect registered too. It is the Practice Studio of the two workspaces of one product ([0025](../docs/decisions/0025-two-studios.md)): it shares music-core, the project file and the design kit with the web app, and its functions are chosen for working with the music at the instrument, not copied from the web app. The design kit is read from `tokens.css` in Daylight and Night with the kit's faces registered at launch (`Design.swift`), and the library is the shelf of cards, each card read from its project file by music-core (`project.summary`).

## Build and run (Mac)

You need Xcode 16 or later, XcodeGen and CMake (`brew install xcodegen cmake`) and the .NET 10 SDK (https://dot.net, or `brew install --cask dotnet-sdk`). Terminal must use Xcode's tools: `sudo xcode-select -s /Applications/Xcode.app/Contents/Developer`.

```bash
cd motiff-lab
git pull
ipad/Core/build.sh          # 2-4 minutes: music-core with NativeAOT; again after music-core changes
ipad/Verovio/build.sh       # 5-10 minutes, once: Verovio from source
dotnet build src/MotiffLab.Web   # the web app's score scripts, which the app's score page runs
cp ipad/App/Config/Local.xcconfig.example ipad/App/Config/Local.xcconfig   # once: your DEVELOPMENT_TEAM
cd ipad/App && xcodegen && open MotiffLab.xcodeproj
```

A `Local.xcconfig` from the old shell (`ios/Config/Local.xcconfig`) can be moved here as it is. Choose the iPad as the destination and Product > Run (Release). Product > Test (⌘U) runs the Swift tests on the chosen device or simulator. A free Apple ID signs the app for 7 days at a time.

## Checks

- The `iPad` workflow (`.github/workflows/ipad.yml`) builds both frameworks, checks the core's C functions on macOS, runs the Swift tests in the iPad simulator and builds for a real iPad, only when asked: on a pull request with the label `ipad-tests`, by hand from the Actions tab (Run workflow on main, which also refreshes the Verovio cache), and for an `ipad-v*` release tag. The build for a real iPad is skipped on pull requests. Run by hand with Screenshots ticked, or for a release tag, it also runs the `Screens` scheme and keeps the pictures as the `ipad-screens` artifact. It is not part of CI's five minutes. Swift written in a cloud session is first compiled there.
- On Linux: `dotnet publish ipad/Core -c Release -r linux-x64 -o /tmp/core && python3 ipad/Core/check.py /tmp/core/MotiffLabCore.so`.

## Releases

A release is a tag `ipad-v<major>.<minor>.<patch>` on main, built in Xcode with `MARKETING_VERSION` set to that number (0019). TestFlight and the App Store need the paid Apple Developer Program.
