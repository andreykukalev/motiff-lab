The list starts with the fourteen behaviours that Andrei had approved, that broke between v0.5 and v0.6.5 and were
restored (the blueprint's R1–R14, here 17 entries). Each says the behaviour as approved now: where his instructions
differ, the newest wins. The restorations of 0.6.4 and 0.6.5 wait for his test of those versions.

## Fields

| Field | What it holds |
| --- | --- |
| Id | Area and number: `SEL` selection, `PLAY` playback, `VIEW` the piece's screen and its views, `ROLL` the piano roll, `SET` Settings, `SCAN` reading a scan, `INK` the stylus and the pen, `ADD` adding a piece, `DRAFT` drafts. An id is never reused. |
| Behaviour | What holds, in the product's words. |
| Approved | Where Andrei's word is: the version, the spec item or his message (`/mnt/project-files/product/versions/`, the version's GitHub issue); then the version that restored it. |
| Status | `approved`: Andrei's word stands. `provisional`: built, not yet confirmed by Andrei, or an open question to him. `known defect`: approved, and the app does not do it now (the bug's issue named). |
| Protected by | One or more, separated by `;`. A test: the path of a file under `tests/backend/Acceptance/`, `tests/ipad/Baseline/` or `tests/contracts/page-scenarios/` in which the entry's id is written (a test's name, a comment or the scenario's data), so `git grep -n SEL-01 -- tests` finds it. A journey of the walk of the screens (Andrei, 2026-11-17 16:01 UTC, thread «Версия 0.7», answer 13): `` `tests/ipad/MotiffLabScreens/<file>` journey `<name>` ``, declared in that file with the entry's id among its `protects:`. `device: <checklist line>`: what only a real iPad shows. `pending: <step>`, with the part it leaves in brackets when a test or a journey protects the rest: the step that writes the test (the blueprint's A4 the UI walk on macOS, A5 a page scenario, B4 a workspace scenario test), or `baseline 0.<n>` for that version's baseline pull request. |

`governance/tests/baseline.test.mjs` (in `build-test`) checks every entry's id, status and «Protected by», that each
test it names exists and names the entry, that each journey it names is declared in the walk's code (not in a comment),
lists the entry and is walked in the asserting walk (not only for the pictures), and that every file under
`tests/ipad/Baseline/` and `tests/contracts/page-scenarios/` (a `README.md` and fixture folders aside) names an entry
that is in the list. Unlike the three test folders, the walk changes without Andrei's label: its files change with
almost every pull request of the interface. A pull request that changes or removes a journey an entry names says so, and
the pull request reviewer checks that the entry is still protected (`governance/roles/pr-reviewer.md`).

## How the list changes

Once per version (the blueprint's section 6.2):

1. **At the tag**, the lead's version note lists what is new as `provisional` entries with ids: the «what to check»
   list.
2. **Andrei tests.** What he accepts becomes `approved`; what he rejects becomes a bug with the entry's id; what he
   changes his mind about replaces the entry, the old row kept with its id struck through (`~~SEL-03~~`) and dated.
   Only his word changes an `approved` entry.
3. **The next version's first pull request** («baseline of 0.x») adds a test for each newly approved entry at the
   cheapest layer that can see it, with his label. A bug he reports gets a test that fails first; if it broke an
   approved entry, that test goes into the protected folders.
4. Every task brief names the entries of its area; every pull request says `UX baseline: unchanged` or lists the
   entries it changes, with Andrei's word for each. The pull request that adds an entry's test replaces its `pending:`
   with the test's path in the same change.

This file, `tests/ipad/Baseline/` and `tests/contracts/page-scenarios/` change only with Andrei's label
`protected-scenarios-ok`, like `tests/backend/Acceptance/` (`governance/README.md`, "Guards").
