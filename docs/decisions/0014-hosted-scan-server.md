# 0014 · A hosted scan server, and a database for what players keep

Status: accepted, 2026-10-28. Andrei chose sign-in with Apple, Google or an email code through Microsoft Entra External ID. The scan server, the API and the sign-in tenant wait on the one-time setup, `infra/azure/setup.ps1` (`infra/README.md`).

## Context

The iOS app cannot carry homr: its AGPL licence keeps it out of an App Store build, and an on-device engine waits on a licence answer or on another model (the research of 2026-10-28, project folder `omr/on-device/`). An app that sends a page to our own server and reads MusicXML back stays closed source, and homr runs unmodified there, as it does on the player's computer (0011). Andrei also wants sessions and imported scores saved in the cloud, in Cosmos DB, rather than only in the browser.

The Azure subscription is shared with an unrelated project. Its Container Apps environments carry a Standard Load Balancer (about $18 a month each) because they use workload profiles and a VNet. A free-tier Cosmos DB account in `rg-shared` (Poland Central) is to be reused, with Motiff Lab's own database in it.

## Decision

### The scan server

1. **The `services/omr` image runs in Azure Container Apps in Poland Central** (`infra/scan.bicep`), in its own group, `rg-motifflab`, in the subscription that holds the Cosmos DB account rather than the web app's (so the API's identity can be given data access in the same tenant, with no keys), in a Consumption-only environment on Azure's own network, with no Log Analytics workspace. Such an environment costs nothing by itself; the app is billed per second only while it reads, and it scales to zero when idle. One copy at most, with 2 cores and 4 GiB (the most a Consumption-only app gets), reading one upload at a time. *Amended in version 0.3* (Andrei, 2026-11-11, with the plan for long recordings): up to 4 copies (`maxReplicas` in `infra/scan.bicep`), each still reading one upload at a time, so the parts of a long recording can be heard side by side; the cap on copies is still what caps the cost.
2. **The image is public on GitHub's container registry** (`ghcr.io/andreykukalev/motiff-omr`), built and deployed by the `Scan server` workflow on each change to `services/omr` on `main`. The repository is public and the service is AGPL, so nothing is lost by a public image, and no registry is paid for. The image's source label points to this repository, which is where homr's source is named.
3. **A PDF may have up to 4 pages when hosted**, not 8: Container Apps ends a request after 240 s, and a page takes up to 40 s on 2 cores.
4. **Browsers may call it only from the web app and its pull request previews** (`ALLOWED_ORIGINS`, `ALLOWED_ORIGIN_REGEX`). A native app sends no origin, and an origin is no protection against a script, so until scanning needs a sign-in, the single copy is what caps the cost of misuse.
5. **Privacy stays as 0011 has it:** the page lives in a temporary folder for the request and is deleted when the answer is sent; nothing about the music is logged, and Container Apps keeps the data in the region. The app asks before each upload to a server that is not on this computer, and the iOS app will show a consent screen and declare user content in its privacy label.
6. **The same server transcribes recordings** (`POST /transcribe`): ffmpeg takes the sound out of an audio or video file and Transkun V2 (MIT, PyTorch on the CPU) returns the notes as MIDI. It was Basic Pitch (Apache-2.0, ONNX) at first, the cheapest choice, but about one note in seven it wrote was an overtone or a split note, and the score looked far harder than the music. Transkun is trained on the piano alone and hears the pedal; on Für Elise synthesised with room reverb and noise it wrote no extra notes and missed one in 905 (Basic Pitch: 15% extra, 19% missed). It costs about a second of the server's two cores per second of sound against 0.05, and 1.5 GB of memory, within the 4 GB the server has; a session costs about 3 cents instead of 2, still mostly the five idle minutes before the server scales to zero. Azure Container Apps waits four minutes for an answer, so the server hears up to 2½ minutes a request, which take about as long to hear. A longer recording, up to 7 minutes, is heard in parts (revised 2026-10-31): the app cuts the sound into stretches of at most two minutes, each sent with five seconds either side, one after another to the one replica, and joins the MIDI that comes back (`RecordingParts` in music-core: each part keeps the notes that start in its stretch, a note heard by both parts at a seam is kept once, a pedal press across a seam stays one). Andrei chose this over a job the app polls or a queue-driven Container Apps job, since the infrastructure stays as it is; 7 minutes take about 7 to 8 minutes to hear. The web app takes the sound out of the recording itself (Web Audio decodes it, mixed to mono at 22,050 Hz, which holds everything Transkun listens to up to 8 kHz), so a video's picture never leaves the device and a few minutes of piano are a few megabytes; only when the browser cannot decode the file is the file sent, up to 50 MB. The server takes up to 200 MB (for the iOS app too). The sound is deleted like a page, the file's name is not sent, the same `Scan` sign-in is asked for, and the notes come back marked detected (`Transcribed`, confidence 0.4), kept with the project as its transcription origin (project file version 9). **The player chooses the stretch to hear** (2026-10-31): once the browser has decoded a recording (files up to 1 GB), Import shows its length and its loudness as 400 bars with a selection window over them, as in an audio trimmer (revised the same day after Andrei tried it): the player drags its edges or the whole window, drags the play position on a strip above the shape (or taps the shape), plays the selection from its start or its last 5 s, moves the position 5 s with buttons or the arrow keys (a focused edge 1 s), plays and pauses with the space bar, and sets an edge to the play position with "Start here" and "End here"; the stretch is at most 7 minutes anywhere in the recording (`RecordingRange` in music-core: moving one end keeps the other when the stretch still fits, otherwise carries it along at the same length). Before sending, it tells how many parts, and so requests, the stretch takes and roughly how long the server listens (about 1.1 s a second of sound sent, the overlaps counted). Only that stretch's sound is sent; the notes' times start at its start. A file the browser cannot decode is still sent as it is, and the server hears its first 2½ minutes. The 7-minute limit is lifted by item 7. **No links** (2026-10-31, Andrei): the app does not take sound from YouTube or any address, on the hosted server or the player's own. YouTube's terms forbid downloading, a service that fetches the music itself is no longer the player's private copy (CJEU, VCAST), and video sites block downloads from cloud addresses; the player picks a file of their own, a video included.
7. **Recordings of any length** (revised 2026-11-11 for version 0.3, Andrei; design note `product/architecture/long-recordings.md`). The 7 minutes were our own limit, set while parts went one at a time to one replica; Transkun and the API set none. Now a stretch is any length, the whole recording by default (`RecordingRange`), and the parts stay about two minutes with five seconds either side. Each seam moves to the quietest half second within 10 s of the even cut, by the loudness the app measures in 100 ms levels (`RecordingParts.Plan`), with no part keeping more than 130 s, so a request carries at most 140 s against the server's 150. A note still sounding when a part's sound ends keeps the length the next part hears it go on for; the dedupe and pedal rules stay. Bars, tempo, key and phrases are still worked out from the joined whole. The web app sends up to 4 parts at once to Motiff Lab's server (maxReplicas 4, `infra/scan.bicep`), one at a time to a player's own; it starts at 2 and adds one as parts come back, drops to one after a 429, 502, 503, 504, lost connection or timeout and asks again after a growing pause (up to 6 tries a part), so a server with one replica is slower but does not fail. Each part heard is kept on the device (IndexedDB) under the sound's fingerprint, the stretch, the server and the part, checked against the engine the server names, until music-core has joined them, so a hearing cut off goes on from the next part; parts left unjoined are deleted after a week. Only the sound of the parts goes, part by part, and the server deletes it as before; no recording is stored on our side. The web app decodes WAV, and where the browser has WebCodecs the AAC or MP3 of MP4, M4A and MOV, a block at a time; other files are decoded whole only up to 120 minutes (30 on a tablet or phone), longer ones get an honest message suggesting WAV, a shorter cut or the iPad app. 40 minutes take about 12 to 15 minutes to hear with 4 replicas; the cost stays about two cores per second of sound.

### The database

7. **Motiff Lab gets its own database, `motifflab`, in the shared free-tier account**, with 400 RU/s shared by its containers, and one container, `projects`, partitioned by `/ownerId`, so each player's projects, sessions and sources sit in one partition. `infra/azure/setup.ps1` creates it once, and first adds up what the account's other databases use, so it stops rather than take the account past the free tier's 1000 RU/s. On 2026-10-30 the account had only 200 RU/s free (cix's `cix` and `cix-live` take 400 each, and 400 is the least a database or container can reserve), so Andrei chose a serverless account of Motiff Lab's own in `rg-motifflab`, billed per request; the script makes it whenever the free tier has no room.
8. **Only the Motiff Lab API reaches the data, with its own identity** (`id-motifflab-api`), allowed into this one database through Cosmos DB's data roles. No account key is used or stored, and nothing on the account or in its other databases changes.
9. **What is stored:** one document per project: its summary for the list, and the project file of 0009 and 0012 (the imported source, sessions, observations, the scan origin), gzip-compressed. A project still over the 2 MB document limit once compressed is refused for now and stays on the device; Blob storage is added only when one first needs it.

### Sign-in and the API

10. **Players sign in with Microsoft Entra External ID**, in its own external tenant: Apple, Google or a one-time code by email. The core is free for the first 50,000 monthly active users. One app registration, *Motiff Lab API*, exposes two scopes, `Projects.ReadWrite` and `Scan`; the web app and, later, the iOS app ask for them. A player is their `oid` in the tenant, the same from every app, and that is the partition their documents sit in.
11. **The API is `src/MotiffLab.Api`**, an ASP.NET Core service in the scan server's environment (`infra/api.bicep`), scaled to zero. It lists, reads, saves and deletes the calling player's projects (`/projects`, `/projects/{id}`) and deletes everything they keep (`DELETE /me`, the right to erasure). A save is a project file; the API reads it with `ProjectFile` before storing it, refuses one that is not that project, and returns an ETag, so a save from a stale copy on another device is refused (`If-Match`, 412) rather than lost. It logs no project content. It also keeps the player's **profile** (Andrei, 2026-11-06): the name and photo they choose to be shown in the apps (`GET`/`PUT /profile`, any plan, a name of up to 60 characters and a JPEG, PNG or WebP of up to 200 KB that the apps cut to a 256-pixel square), one more document in the player's partition, erased with everything else by `DELETE /me`. Without one the apps show the sign-in's name, passing over External ID's "unknown" for a player who gave none (music-core's `Accounts.PlayerName`).
12. **The hosted scan server reads a page only with a token that carries `Scan`** once `AUTH_AUTHORITY` and `AUTH_AUDIENCE` are set; on the player's own computer nothing is checked, as before.
13. **Saving online is the player's choice, never the default.** The rule that imports never leave the device (CLAUDE.md, 0011) becomes: nothing leaves the device unless the player signs in and turns on saving online, and then only to this API. *Amended in version 0.2* (Andrei, 2026-11-11, «согласен» to new pieces and their changes going between the devices by themselves): signing in is the player's choice and turns saving online on, so the pieces sync; Settings turns it off on each device. Nothing leaves the device while signed out, and still only to this API.
14. **The web app signs in with MSAL** (`Microsoft.Authentication.WebAssembly.Msal`, redirect mode) only when `wwwroot/appsettings.json` names the tenant, the web app's client id, the scopes and the API's address (`Account`, public identifiers); with it empty, nothing about accounts shows. The committed file is empty: CI fills it in for the deployed app, on `main` only, from the repository variables `infra/azure/setup.ps1` sets. Settings signs in and out, turns saving online on (which sends the projects already on the device), and deletes everything online. The device stays the working copy: each save goes to IndexedDB first and to the API three seconds after the last change, the last save wins, and a failed upload only shows on Settings. Home lists projects saved online from another device, fetched when the player asks. *Amended in version 0.2* (sync, [0025](0025-two-studios.md) section 8): the web and the iPad send each save with `If-Match` and fetch what changed online by themselves, when the library opens, comes back into view or the network returns; when both changed one piece, the last save wins and the other copy is kept beside as a piece of its own, on the device; saving online is free up to 300 pieces (`ProjectSync`, `Account/CloudSync.cs`, `ipad/App/MotiffLab/CloudSync.swift`). The Scan token goes only to the hosted scan server's address (`Account:Scan`), never to an address typed in Settings.

### Two environments

15. **develop has its own servers and data** (version 0.3; Andrei chose a separate resource group, 2026-11-11 22:31 UTC). `rg-motifflab-dev`, in the same subscription and region, holds the Container Apps environment `cae-motifflab-dev` with `ca-motifflab-api-dev` and `ca-motifflab-scan-dev`, a serverless Cosmos DB account of its own with the same `motifflab` database and `projects` container, the API's identity `id-motifflab-api-dev` (that database only), and a CI identity, `id-motifflab-github-dev`, that signs in from `develop` and may change this group only (`infra/dev-env.bicep`, set up once by `infra/azure/dev-env.ps1`). The same `api.bicep` and `scan.bicep` deploy both (`branch` main or develop). A push to `develop` deploys develop's servers at once, without approval; `main` deploys as before, after Andrei's approval in the Environment `production`. The web test site and the iPad's version builds (tags `v0.<n>` not yet in `main`) use develop's servers (`API_URL_DEV`, `SCAN_URL_DEV`; `ipad/build-version.sh` reads them from the test site), so what a version saves lives in the test database, never next to the players' real data, and reaches the main one only through the released version or an export. Shared, because a second one would cost more than it gives: the sign-in tenant (the same accounts and roles), the Static Web App (its environment `develop` is the test site) and the images (tagged by commit). Removing the group removes everything for develop. Rejected: the same group with `-dev` names, which mixes test and real data and leaves CI from `develop` Contributor next to the real database. Details: `infra/README.md`, "The develop environment".

## Consequences

- The scan server's cold start pulls a 2 GB image, so the first page after an idle spell can take a minute or two longer. Raising `minReplicas` to 1 would remove that but bill around the clock.
- Beyond Container Apps' monthly free grant (180,000 vCPU-seconds and 360,000 GiB-seconds per subscription, which the other project's apps share), a page costs about a quarter of a cent, and the copy then waits five minutes at the idle rate (about half a cent) before it scales to zero, so the next page of a session starts warm.
- The web app's Static Web App moved into `rg-motifflab` too (Andrei, 2026-10-30), so everything Motiff Lab runs is in one group and one subscription and CI deploys it all as one identity. Azure cannot move a resource to a subscription of another tenant, so `infra/azure/setup.ps1` creates a new one with a new address (`WEB_HOST`), which the sign-in redirect URIs, the scan server's and the API's allowed origins and the iPad app follow.
- The player's own computer stays an option: Settings still takes any address, and `http://localhost:8765` still works offline.
- Where the build has sign-in, Settings offers Motiff Lab's server (chosen until the player picks another or turns scanning off), their own server (its Docker commands folded under "How to run your own server") or Off. Nothing goes to the hosted server before the player signs in, and each page and recording still asks first; Import shows Sign in and Create an account where scanning needs them (2026-10-30, Andrei asked for sign-in and Settings to work like familiar apps).
