# 0020 · The music-core facade: one JSON contract for the web app and the iPad app

Status: proposed, 2026-11-01. Andrei asked for one stable API with JSON in and out, shared by the web app and the native iPad app, with the project file as the contract between them (redesign preparation, item 21). Number 0019 (the native iPad app) is reserved for a record still to be written; the redesign is [0018](0018-redesign.md).

## Context

The web app calls music-core directly from Razor code: `PlaybackLab.razor` alone imports a piece, suggests phrases, selects a passage, analyses it, offers experiments, drives a variation chain, generates notation and playback scores and saves the project, with the orchestration spread over two thousand lines of UI code. The spike `spikes/ios-core` (PR #176) showed that the same C# music-core runs natively on the iPad through NativeAOT, and that Verovio engraves its MEI there in about 50 ms. The redesigned iPad app is native Swift ([[0015]] is superseded by [[0019]]), so Swift needs a way to call music-core, and the redesigned web app needs the same orchestration without copying it from the old page.

Options weighed:

- **Rewrite music-core in Swift.** Two engines to keep equal, tested twice; the analysis, catalogue and project file are the product. Rejected by Andrei.
- **Expose the C# types to Swift one by one.** NativeAOT exports only C functions with plain arguments; every record would need a hand-written marshalling layer, and every change in music-core would change the C surface.
- **A facade with JSON in and out (chosen).** The C surface stays at five functions. The contract is the list of calls and the shape of their JSON, versioned; music-core can change behind it. The web app (Blazor, C#) calls the same facade class, so the two clients exercise one orchestration and one set of tests.

## Decision

1. **`MotiffLab.MusicCore.Facade.MusicCoreFacade`** is the one entry point for an app. It keeps the pieces an app has open in memory, numbered from 1, and answers calls by name with JSON text. It is the only stateful part of music-core: everything under it stays pure, and the facade itself is deterministic (the same calls in the same order give the same answers).
   - `Open(fileName, bytes, language)` imports a MIDI or MusicXML file as a new project, or reads a project file (`.motiff.json`), and returns the piece's number with its summary. A rejected file answers with the importer's reason and tip.
   - `Call(piece, name, request)` runs one call on an open piece; `piece` 0 is for the stateless calls (`version`, `catalogue`, `settings`, `settings.state`). `request` is a JSON object or null.
   - `Close(piece)` forgets it.
   - Every answer is one JSON object. A failure is `{"error": code, "message": text}` and leaves the piece as it was. Codes: `import`, `noPiece`, `unknownCall`, `badRequest`, `noSelection`, `noVariation`, `unavailable`, `internal`.
2. **The contract is versioned.** `version` returns `{"contract": 4, "projectFile": 13, "runtime": …}`. A field is added without changing the contract number; a field removed or renamed, or a call's meaning changed, raises it. The project file version ([[ProjectFile.Version]], 13, described in [docs/project-file.md](../project-file.md)) is part of the contract: the file an app saves is what the other app opens and what the API stores (0014). Contract 2 (2026-11-01, redesign package 2) replaced `sessions` and `observations` in the project summary with `resumePoints`, `ideas`, `marks`, `bookmarks` and `openChecks`, and added the calls below the line in the table. Contract 3 (2026-11-01, redesign package 3, preparation items 7–9) brought the three phrase levels of [[0018]] section 3: `phrases` answers the level shown and the units of a level with their parent, `long` replaced `fitsSelection`, the levels are `short`, `phrase` and `sentence` (all available; `period` is gone), `phrases.level` and `phrases.edit` take a level and `split`, `understand` ranks the facts (`strongest`, `keyObservation`) and gives every fact its Try chips, and `try` sounds a chip. Within contract 3, `notation` gained `bars` and `ossia` for an excerpt with ossias above it (preparation item 10, [[0021]]), answered as `excerpt` and `ossias`, a field added; `understand` gained `harmony` (preparation item 19), a field added. Within contract 3, `dna` (preparation item 18, [[0018]] section 11), until then a placeholder answering `{"status": "notYet"}`, answers the Piece DNA lanes, each with its `status` (`notYet`, `partial`, `ready`), so a screen shows an empty state for a lane not analysed yet and later analyses only fill the contract: `form` (sections, not analysed yet), `ideas` (until the main motifs are found, the selection with its exact and transposed repeats), `keys` (the file's key signatures, with the mode chosen from the notes when the file gives none) and `newMaterial` (bars whose line repeats no earlier bar). Contract 4 (2026-11-05, [[0022]]) carries project file version 13 with the performances compared with the piece, and adds the `performance` calls: `performances` lists them; `performance` answers one compared with the piece bar by bar (whether the bar lines up, its kind, the marker text, the confidence, whether it was dismissed or taken, and the notes on each side); `performance.add` takes a MIDI file in base64 (the transcription engine's or the player's), lines it up, raises the `Performance` Check flags on a scanned piece and answers the comparison; `performance.take` and `performance.restore` take bars into the score or bring the print back, and `piece`, `notation` and the analyses then read the notes with the bars taken; `performance.dismiss`, `performance.rename` and `performance.remove` do what they say. Within contract 4, the project summary gained `checkBars`, `hasNotes`, `document` and `latest` (the resume point worked from last: `id`, `name`, `at`, `lastActive`), fields added, and `project.summary` (piece 0) answers it for a project file sent as `file`, without opening the piece, for the iPad library's cards (2026-11-05); a phrase unit gained `name` (2026-11-05), and `roll` answers the piano roll's data, the packing the web app's roll read until then from its own code (2026-11-05). Within contract 4, `performance.add` also takes `file` (base64) with its `fileName`, a MIDI or MusicXML file of another version, and a version's `source` can be `score` (2026-11-05, [[0022]] section 1), fields added. Within contract 4, the project summary gained `readFrom`, the PDF piece notes were read from (2026-11-05, [[0023]]), a field added. Within contract 4, a PDF opens as a PDF piece with the `document` calls (2026-11-05, [[0023]], for the iPad app's PDF view), calls added.
3. **JSON is written and read by hand** (`Utf8JsonWriter`, `JsonDocument`), as the project file is, so the output is fixed and NativeAOT needs no reflection. Ticks are integers at 480 per quarter ([[0002]]); enums are lower camel case names; what music-core inferred carries its provenance and confidence as the events do ([[0004]]). The parameters of a variation step use the project file's shape, so a step can be copied between a saved project and a request unchanged.
4. **Words follow the piece.** `Open` takes a language tag (`en`, `ru`); `language` changes it. Every text in an answer (facts, phrase descriptions, operation names, explanations) comes from music-core's `Words`, never from the client.
5. **The web app moves onto the facade in the redesign**, not before: the current page keeps its direct calls until it is replaced. The iPad app calls the facade through five C functions exported by the native build (`ml_version`, `ml_open`, `ml_call`, `ml_close`, `ml_free`), each returning UTF-8 JSON the caller frees. The spike's benchmark exports stay only in the spike.

## The calls

Request fields are optional unless marked; a tick span is `{"onset", "end"}`; a note is `{"id", "pitch", "onset", "duration", "velocity", "track", "voice"?, "hand"?: "left" | "right", "handInferred"?, "provenance"}`.

Calls kept for the next contract version: note corrections (S1-I7), MIDI export, the Keep table's parameter choices (today a UI list), and the fact digest for AI (0003).

## Consequences

- One orchestration, tested once: `tests/MotiffLab.MusicCore.Tests/Facade` asserts the JSON of every call on the test pieces; a Swift test in the spike checks the same answers through the C functions in the simulator.
- A request costs a JSON round trip. On the iPad it is tens of microseconds against tens of milliseconds of analysis; in Blazor WebAssembly it is slower, which is one more reason the web app moves only with the redesign, where it can measure.
- The facade holds state, so an app must call it from one thread at a time per piece (the spike runs music-core on its own 8 MB thread).
- Changing a music-core type no longer changes the clients until the contract changes; the record of what changed lives in the contract version's comment, as it does for the project file.
