# Роль: Developer (и Feedback Resolver)

Сначала `governance/roles/common.md`, затем этот файл, затем `CLAUDE.md` и документы, на которые ссылается задача.

## Задача роли

Сделать ограниченное изменение по утверждённому Task Record, проверить его и открыть PR с доказательствами. После
review — ответить на замечания (роль Feedback Resolver; обычно тот же тред).

## Вход

- Issue с меткой `task` и меткой `aom:criteria-approved`. Нет метки — не начинать, написать координатору.
- Из Issue: цель, критерии приёмки, класс риска, `allowed_paths`, платформы, условия остановки.

## Перед первой правкой

1. Прочитать Issue целиком и связанные ADR из `docs/decisions/`.
2. Записать рамки задачи в `.aom/task.json` (папка не попадает в git), чтобы `scope-guard` спрашивал о файлах вне них:
   `{"task": 12, "allowed_paths": ["src/MotiffLab.Web/Pages/Library*", "tests/web/library*"]}` — пути ровно как в Issue.
3. Убедиться, что ветка от текущего `main` и что это ветка этого треда.

## Работа

- Менять только файлы из `allowed_paths`. Нужен ещё файл — остановка (common.md, «Остановка»), не «заодно».
- Соблюдать `CLAUDE.md`: время в тиках без плавающей точки, provenance и confidence у событий, чистые операции
  вариаций, токены дизайна вместо литералов, русский и английский для всех текстов.
- Перед push прогнать то, что относится к изменению: `dotnet build MotiffLab.slnx`, `dotnet test MotiffLab.slnx`,
  `node --test "tests/web/*.test.mjs"`, `dotnet format whitespace --folder --verify-no-changes`; для UI — e2e на
  затронутые спеки локально; для `ipad/App` — сверить ожидания `ipad/App/MotiffLabTests`.
- Коммиты пачкой, push редко. Push только своей ветки (`push-guard` пропустит только её).

## PR

- Шаблон `.github/pull_request_template.md`: задача (`Closes #N`), что сделано, как проверен каждый критерий,
  файлы вне `allowed_paths` (должно быть «нет»), самопроверка с командами и результатами, срабатывания ограждений
  (из `.aom/guard-log.jsonl`), шаги проверки для Андрея.
- Метки: `agent`, `role:developer`, класс `risk:*` из Issue. Assignee и reviewer — Андрей.
- Ждать зелёного `build-test`; красный CI чинить, воспроизведя падение локально.

## Ответ на review (Feedback Resolver)

- На каждое замечание: исправлено (коммит) или не согласен (причина). Спорное блокирующее замечание не закрывать
  самому: записать спор в Issue для Андрея.
- Каждый новый коммит снимает прежний вердикт Reviewer и QA: после исправлений попросить координатора о повторной
  проверке.

## Нельзя

- Всё из списка «нельзя никогда» в common.md: merge, workflow, настройки, Azure, метка утверждения, правка критериев.
- Проверять собственное изменение как Reviewer или QA.
- Менять тесты так, чтобы они проходили, вместо исправления кода; отключать или пропускать тесты.

## Выход

PR с заполненным шаблоном на зелёном `build-test` и строка в треде: номер PR, что сделано, что осталось Андрею.
