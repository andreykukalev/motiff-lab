# Общие правила процесса

Этот файл читает каждый агент, который работает над Motiff Lab, до начала задачи, вместе с файлом своей роли из этой
папки. Правила продукта и кода — в `CLAUDE.md`, здесь только то, как идёт работа. Основа — Agent Operating Model v1.3
(модель A, Controlled Autonomy) и Agent Environment Architecture, раздел «Текущий выбор: фундамент и мягкий режим».

Этот файл, файлы ролей, `.claude/`, `.github/`, `CLAUDE.md` и `tests/acceptance/` — среда агентов. Их меняет только
задача среды класса E3, а применяет Андрей. Агент не меняет правила, по которым работает сам, и не расширяет свои права.

## Где мы сейчас

- Режим — **мягкий A1**: агенты работают в тредах проекта claude.ai (и, если Андрей запускает, в Claude Code на его
  компьютере), а все действия в GitHub идут от имени Андрея. Роли разделены процессом, а не identity.
- Пока фундамент не применён, действует **A0**: только исследование и документы, без записи в репозиторий, GitHub,
  Azure и CI. Что применено, видно в `main`: есть ли этот файл, `.claude/settings.json` и ruleset на `main`.
- Модели оплачиваются только подпиской Андрея. Ключи API и купленные токены не предлагаются.
- Одна задача за раз. Вторая параллельная задача (A2) и auto-merge (B1) возможны только в строгом режиме.

## Источник истины

- Задача — это **Task Record**: Issue по форме `.github/ISSUE_TEMPLATE/task-record.yml` с меткой `task`.
  Доказательства — в PR, который на неё ссылается (`Closes #N`). Чат, память проекта и `/mnt/project-files/` —
  рабочие заметки: они не меняют ни критериев, ни рамок, ни статуса задачи.
- **Критерии приёмки утверждает Андрей до реализации**: он ставит метку `aom:criteria-approved` сам. Агент эту метку
  не ставит и не снимает. Без неё Developer не начинает.
- После утверждения критерии не правятся. Если они неверны или неполны, агент останавливается и пишет об этом в
  Issue; изменение — решение Андрея. Если меняется сама цель — новая задача.
- Класс риска только повышается: любая роль может поднять его одной строкой причины в Issue; понижает только Андрей.
  Минимум задаёт таблица путей AOM (раздел «Классификация рисков»): `.github/`, `infra/`, `governance/`, `.claude/`,
  `CLAUDE.md` — Guardrail; facade, файл проекта, `ipad/Core`, `src/MotiffLab.Api`, `services/omr`, `Scripts`, `i18n`,
  `PlaybackLab*`, `src/MotiffLab.MusicCore` (пока API деплоится на его изменения) — High; остальной `src`, `ipad/App`,
  `design/kit`, `tests`, `docs/decisions` — Standard; `docs`, `README.md` — Low; всё, что не перечислено, — Standard.

## Как идёт задача

1. **Intake.** Андрей или координатор заводит Issue по форме: цель, критерии, класс, компоненты, `allowed_paths`,
   платформы, условия остановки.
2. **Утверждение.** Андрей проверяет критерии и ставит `aom:criteria-approved`.
3. **Developer** — отдельный тред. Делает изменение в своей ветке, проверяет, открывает PR по шаблону
   (`.github/pull_request_template.md`) с метками `agent`, `role:developer` и классом `risk:*`.
4. **CI** `build-test` зелёный на последнем коммите PR. Ruleset на `main` не даёт слить PR без него.
5. **Reviewer** — новый тред со свежим контекстом. Видит только Task Record и PR, не тред Developer. Пишет отчёт
   в PR (`governance/roles/reviewer.md`).
6. **Исправления.** Developer (как Feedback Resolver) отвечает на замечания новыми коммитами; каждый новый коммит
   снимает прежний вердикт: review и QA действуют только для того SHA, который проверили.
7. **QA** проверяет каждый утверждённый критерий на последнем SHA и готовит шаги проверки для Андрея
   (`governance/roles/qa.md`). Для класса Low Reviewer и QA может быть один тред.
8. **Признание и merge.** Андрей проверяет результат (для UI — на dev-сайте или на iPad) и **сам** сливает PR.
9. **Метрики.** После merge Андрей запускает `node governance/metrics/collect.mjs task <issue>`
   (`governance/metrics/README.md`).

## Что агенту нельзя никогда

- Сливать PR, включать auto-merge, одобрять деплой, запускать или перезапускать workflow вручную.
- Пушить в `main`, в чужие ветки, с force, удалять ветки, пушить теги.
- Менять настройки GitHub (rulesets, Environments, секреты, переменные, метки репозитория, видимость) и что-либо в
  Azure. Скрипты `infra/azure/*.ps1` и `infra/github/*.ps1` запускает только Андрей.
- Ставить или снимать `aom:criteria-approved`, править утверждённые критерии, понижать класс риска.
- Пользоваться компьютером Андрея (папки, Desktop Commander, Remote Control) и его почтой, календарём, диском.
- Обходить ограждение, когда оно сработало (другой командой, другим инструментом, через скрипт).

## Ветки, коммиты и PR

- Работа идёт в ветке, которую дал тред (`claude/project-thread-*`), или в `task/<номер>-<кратко>`. В `main` попадает
  только PR, который сливает Андрей.
- Одна задача — одна ветка — один PR. Изменения вне `allowed_paths` не добавляются «заодно».
- В сообщениях коммитов и описаниях PR указываются требования (`S1-…`, `V1–V12`, `FR-…`), когда код их реализует.
  Трейлер `Claude-Session` в коммитах сохраняется: по нему метрики отличают коммиты агента от коммитов Андрея.
- Коммиты собираются пачкой, пушатся редко: каждый push запускает CI. Не пушить ветку, чтобы «сбросить» её, не делать
  пустых коммитов и не переоткрывать PR ради CI.
- PR начинается с блока атрибуции, который требует платформа, затем разделы шаблона.

## CI и тяжёлые проверки

- CI держится в 5 минутах (таймаут job `build-test`): whitespace, сборка, unit- и TypeScript-тесты, тесты ограждений.
- Браузерные тесты (`tests/e2e`) в CI запускаются только по просьбе Андрея: метка `browser-tests` или ручной запуск CI.
  Агент сам гоняет их локально для тех спеков, которые трогает.
- iPad-сборка на macOS — только по метке `ipad-tests` или по тегу `ipad-v*`, и только когда Андрей согласен. До
  первого такого запуска агент сверяет ожидания в `ipad/App/MotiffLabTests` (число страниц, ключи i18n, счётчики
  DOM в `score.js`) и правит их в том же коммите: Swift в контейнере не собирается.
- Деплой в Azure (`api.yml`, `scan-server.yml`) ждёт одобрения Андрея в Environment `production`. Сайт (dev) обновляется
  сам после зелёного CI на `main`; iPad-приложение (prod) — только релизами, вместе с вебом.

## Продуктовые решения

- Для редизайнов интерфейса и механик сначала варианты дизайна на согласование; PR — только после согласия Андрея.
- Открытые вопросы из `design/kit/HANDOFF.md` (раздел 7) и любые продуктовые развилки решает Андрей, а не агент.

## Остановка

Агент останавливается и спрашивает, а не решает сам, если:

- нужен файл вне `allowed_paths`, или изменение задевает контракт (facade JSON, файл проекта, HTTP API, Cosmos);
- нужно право или действие из списка «нельзя никогда»;
- критерии неясны, противоречат друг другу или не решают задачу;
- класс риска по факту выше, чем в Task Record;
- сработало ограждение (deny, hook, отказ ruleset).

Остановка оформляется комментарием в Issue (и строкой в треде): что делал, что упёрлось, какие варианты, что нужно от
Андрея. Остановка — правильный результат, а не провал: учения на неё (метрика M8) проводятся намеренно.

## Ограждения

В мягком режиме у всех агентов одна identity — Андрей, поэтому ограждения ловят ошибку, но не делают её невозможной.

| Ограждение | Где | Что делает |
| --- | --- | --- |
| Ruleset `main` | GitHub | Только PR, обязательный `build-test`, без force-push и удаления; обхода нет ни у кого |
| Environment `production` | GitHub | Деплой API и сервера распознавания ждёт нажатия Андрея |
| Deny | `.claude/settings.json` | Запрещает merge, auto-merge, запуск workflow, запись файлов через GitHub API, force-push, правку rulesets и Environments, Azure CLI, компьютер и почту Андрея |
| `push-guard` | `.claude/hooks` | Пускает push только текущей ветки агента в `origin`; отказывает в `gh`-командах, которые сливают, запускают, выпускают и меняют настройки, и в записи в GitHub API |
| `scope-guard` | `.claude/hooks` | Спрашивает перед правкой среды агентов вне задачи среды и перед правкой вне `allowed_paths` из `.aom/task.json` |
| env-scope | CI | Помечает PR, который меняет среду агентов (предупреждение, не запрет) |

Проверка 2026-11-08: в облачном треде claude.ai `.claude/settings.json` репозитория не применился — запрещённая
команда выполнилась, `scope-guard` не спросил, агенты из `.claude/agents` не нашлись. Пока это не исправлено, в
облачных тредах держат только ruleset, Environment и эти правила. В Claude Code на компьютере deny и hooks должны
действовать, но это ещё не проверено [не проверено].

Каждый отказ и вопрос hooks записывается в `.aom/guard-log.jsonl`. Developer переносит их в раздел PR «Срабатывания
ограждений». Любая попытка обойти ограждение — инцидент: весь мягкий режим возвращается на шаг назад до разбора с
Андреем (AOM, «Откат автономии»).

## Координатор (Orchestrator в мягком режиме)

- Помогает Андрею сформулировать Task Record, заводит Issue, следит за ходом, но не пишет код и не решает споры.
- Выбирает роль по намерению Андрея по таблице `governance/routing.md`; если Андрей назвал роль сам — зовёт её.
- Архитектурные и продуктовые развилки отдаёт совету (`governance/roles/council.md`), а не решает сам.
- Запускает роли отдельными тредами: Developer, затем Reviewer (новый тред, без пересказа рассуждений Developer —
  только номер Issue и PR), затем QA. Сам не сливает и не просит треды слить.
- Одна задача в работе за раз. Следующая начинается после merge или отмены текущей.
- Не переназначает ревьюера ради другого ответа и не снимает замечания; спор записывает в Issue для Андрея.
